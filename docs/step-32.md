# step-32：黄金问答集与跑分脚本

## 目标

此前所有"验证"都是改完手动问一句、看着还行。
没有尺子，任何优化（换切分策略、调相似度阈值、改提示词、加 rerank）
都无法判断是涨还是跌——这正是前面 31 步一直没敢大动 RAG 的原因。

本步落地最小可用的评估体系：**黄金问答集 + 两层分离的跑分脚本**。
它本身不改动任何线上链路，后续每一步都可以拿它做回归。

## 实现要点

### 1. 黄金集格式（`data/eval/golden.jsonl`）

一行一个 JSON 对象，字段刻意压到 6 个：

| 字段 | 层 | 含义 |
|---|---|---|
| `id` | — | 稳定标识，跨版本对比时按 id 逐条对齐 |
| `category` | — | 分组统计（退货/退款/物流/转人工/超范围…） |
| `question` | — | 用户提问原文 |
| `expect_sources` | 检索 | 期望命中的知识库文件名，空数组=不校验检索 |
| `expect_points` | 生成 | 答案**必须全部**出现的要点（AND） |
| `expect_any` | 生成 | 答案**至少出现一个**的要点（OR） |
| `expect_transfer` | 生成 | `true`/`false` 校验转人工行为，`null`/省略=不校验 |

现有 30 条，13 个分类：业务问答 25 条 + 转人工 2 条 + 超范围 2 条 + 知识库外 1 条。

选 JSONL 而不是 YAML/CSV：人工维护、diff 友好，且**按行校验**能直接报出
"第 N 行有问题"，改起来不用在嵌套结构里找。

### 2. 加载即校验（`app/eval/dataset.py`）

黄金集是尺子，尺子自己会腐化：知识库文件改名、政策数字变了、手写 JSON 漏字段。
如果腐化只在跑分时表现为"分数掉了"，排查成本极高。所以加载阶段就硬校验：

- **`expect_sources` 的文件必须真实存在于知识库目录**——这条最关键。
  改文件名/删文件时会在跑分前直接失败，并提示现有文件名。
- `id` 唯一（否则跨版本对比会错位）
- `expect_transfer` 只能是 bool 或 null（写 `"yes"` 会静默变成真值，必须拦）
- 每行必须是合法 JSON，报错带行号

### 3. 打分是纯函数（`app/eval/metrics.py`）

打分逻辑不碰 Milvus / LLM / Postgres，全部是纯函数。
这样"尺子准不准"能在 1 秒内单测验证，不用起中间件、不用花 LLM 费用。
如果打分埋在跑分脚本里，就只能靠跑一次全量来试——慢、贵，而且分不清
"模型变差了"还是"打分写错了"。

几个刻意的设计：

- **`normalize()`**：NFKC 全角转半角 + 去空白 + 小写。
  LLM 每次措辞不同，"7 天"/"7天"/"７天"是同一件事，
  因空格判错要点缺失会让整个评估结论不可信。
- **检索判据是 recall 而非 top1**：只要期望文件出现在 top_k 里就算命中。
  父子检索本就允许多来源命中，排序质量另看分数分布。
- **`expect_points` 是 AND，`expect_any` 是 OR**：
  "7 天 + 无理由"少一个就是没答全；而超范围问题只能用 OR
  （"帮不了/无法/抱歉"任一措辞都算合格）。
- **误转与漏转分开统计**：处置方向完全不同。
  误转（该自助却推给人工）是体验与成本问题；漏转（该转没转）是服务问题。
  混成一个"转接准确率"看不出该往哪边调。
- **分母只算"实际校验过的条数"**：只跑检索层时，转人工用例没有可校验项，
  既不能算失败（CI 永远红），也不能算通过（通过率虚高），单独计入 `unchecked`。

### 4. 两层分开跑（`app/eval/runner.py`）

```
检索层 run_retrieval：store.search → 期望来源是否命中      （无 LLM，毫秒级）
生成层 run_full     ：完整 LangGraph 图 → 要点 + 转接行为   （有 LLM，慢且花钱）
```

**分层是为了归因**。只跑生成层时，"答案不对"到底是
"没检索到"还是"检索到了但没答好"永远说不清。
拆开后：检索命中率高而答案通过率低 = 提示词/生成问题；
两者一起低 = 知识库/切分问题。

对应到使用场景：

- 检索层 → 进 CI，每次改切分/embedding/阈值都跑（`uv run python scripts/run_eval.py`）
- 生成层 → 发版前、改提示词后手动跑（`--full`）

生成层每条用例用**独立 thread_id**：避免上一条的 Checkpointer 记忆污染下一条
（评估必须可复现），代价是每条都冷启动，与真实首次提问一致。

### 5. 评估数据必须清理（踩到的真坑）

转接工具 `transfer_to_human` 写的是**真表** `conversation_status`，
Checkpointer 也会留快照。不清理的后果：

- 坐席端队列里出现一批"评估用例"待接工单
- 表随评估次数无限增长

处理方式：`run_full` 的 `finally` 里统一清理（状态表 + `adelete_thread`）。
但进程被 Ctrl-C / SIGTERM 时 `finally` 不一定执行，所以另给
`--purge` 兜底：只按 `eval-` 前缀删，不碰任何真实会话。

### 6. 限流噪声必须与质量失败区分

实测厂商限流是 **1 分钟 10 次请求**，而一条用例平均 2 次 LLM 调用。
第一轮全量跑分在第 18 条开始成片 429，两条用例被判失败——
差点被误读成"模型答不好账号类问题"。

两个修正：

- `--delay`：用例间隔秒数（限流厂商下设 12 左右）。
- `error` 字段 + 汇总里的"执行异常 N 条"：异常摘要随结果带出，
  输出行直接显示 `无回复（RateLimitError: 429）`，
  与"缺点:xxx"这类质量失败一眼可分。

顺带修掉一个归因缺陷：检索层与生成层原本共用一个 `try`，
LLM 抛异常时 `store.search` 根本没执行，于是**检索也被记成未命中**——
两层分开统计的意义当场失效。已拆成两个独立的 `try`。

### 7. 顺带修掉的两个既有缺陷

这两个都是跑本步时被真实触发的，不是主动重构：

1. **`runtime.get_checkpointer()` 是死代码，调用即永久挂起。**
   它等的是一个 `asyncio.Future`，而 `set_result` 在 step-29.9 清理时被删掉了，
   `get_graph()` 里再没人给它赋值。评估脚本第一次跑就卡在这里（2 条用例跑了 3 分钟没退出）。
   已删除该函数与 `_checkpointer_ready`，评估改为从 `graph.checkpointer` 取——
   图本来就是 Checkpointer 唯一的使用者，多一层访问器只会多一条会失效的路径。

2. **`app/main.py` lifespan 里 `runtime.close()` 漏了 `await`。**
   `close()` 是协程，不 await 等于创建了个没人执行的协程对象，
   连接池在应用关闭时从未被真正释放（只在进程退出时随 OS 回收）。

## 常用命令

```bash
uv run python scripts/run_eval.py                          # 检索层（无 LLM，秒级）
uv run python scripts/run_eval.py --full                   # 完整链路
uv run python scripts/run_eval.py --full --delay 12        # 带限流厂商
uv run python scripts/run_eval.py --full --category 退货 --verbose
uv run python scripts/run_eval.py --full --ids returns-1,refund-1
uv run python scripts/run_eval.py --full --json /tmp/e1.json   # 落盘对比
uv run python scripts/run_eval.py --purge                  # 清理中断跑分的残留
```

有未通过用例时退出码为 1，可直接做发版门禁。

## 遗留问题

**最重要的一条：100% 说明这套题太容易，现在还测不出改进。**

当前语料只有 10 个文件 31 个块，`top_k=3` 就能覆盖 3 个文件，
25 条业务问答题全命中并不意外。也就是说：
现在加 rerank、加 query 改写，分数大概率还是 100%，**测不出收益**。
下一步要让黄金集变"难"：

- **同义改写**：不出现知识库原词（如"东西拆了能退不"而非"无理由退货"）
- **多跳问题**：一条回答需要跨两个文件（如"退货后退款多久到账 + 运费谁出"）
- **易混淆**：退货(7天)/换货(15天)、退货邮费 vs 换货运费，考检索是否抓对文件
- **知识库外**：现在只有 1 条，且判定很宽
- **多轮指代**：当前每用例独立 thread，测不到"那它能退吗"这类追问

其他：

- 答案要点匹配仍是字符串包含，同义表达会误判 → 后续可上 LLM-as-judge 做二次判定
- 生成层 LLM 有随机性，单次跑分的波动幅度未测量 → 需要重复跑 3 次看方差，或固定 `temperature=0`
- 未接入 CI（检索层已经够快，可以接；生成层要限流 + 花钱，更适合手动）
- 误转/漏转的"可接受阈值"要等有真实用户日志才能定，现在 0 条不代表没问题
- 评估只覆盖单轮首问，坐席端与转接后的消息链路不在评估范围内
